# Findings, 2026-10-09: build times, shared front end, drag fixes, TaskbarWidgets

Summary of one working session on the taskbar widgets (bus, weather, media) and the shared
library `taskbar-dock`. Measurements are from this PC (RTX 3070 box, Windows 11), taken the
same day.

## Summary

- **Build time:** splitting the widgets into front-end and back-end crates (the Reddit
  "1000 crates" idea) would not help. Our crates are 2–5k lines; an edited widget rebuilds in
  ~0.8 s with the `fast` profile. The slow part is the full-LTO `release` build (13–15 s), and
  LTO optimises all crates together however they're split.
- **Edit loop:** most of `dev.ps1`'s time was fixed sleeps. Replaced with waits that end as
  soon as the widget is stopped / has started: the `-Fast` loop for the bus widget went from
  5.6 s to 1.0 s.
- **Shared front end:** new module `strip` (glide into the slot, drag, zoom while held). All
  three widgets use it; `panel` already shared the popup rules. A shared popup *host* isn't
  worth it (see below).
- **Bug fixed:** dragging a wide strip (media) to the far right didn't take that place. The
  slot rule in `dock::insert_index` is now "the slot nearest to where it's held".
- **From TaskbarWidgets (pfcdev):** adopted re-anchoring the grab point when the strip is held
  against the tray. Candidate next step: treat taskbar app icons as obstacles.

## 1. Build times

Measured on `taskbar-media` and `buswidget` after a real one-line code change:

| Build | bus | media |
|---|---|---|
| `fast` profile (no LTO, incremental) | 0.8 s | 1.2 s |
| `fast` tests (`--no-run`) | 0.7 s | 1.1 s |
| `release` (fat LTO, 1 codegen unit) | 15.3 s | ~10 s |
| a `taskbar-dock` file changed, widget `fast` build | 1.1 s | 1.0 s |

- The Reddit thread was about single crates of ~100k lines where rustc's front end can't feed
  LLVM fast enough. That isn't our situation.
- More crates wouldn't shorten `release`: LTO re-optimises everything as one unit.
- Each widget has its own `target\`, so `taskbar-dock` is compiled once per widget. A Cargo
  workspace would share it, but that only helps clean builds (not done).

## 2. Edit loop (`taskbar-dock\scripts\dev.ps1`)

Before: build, test, then stop → sleep 0.4 s → copy → start → sleep 3 s. Now:

- **Stop:** `Stop-Process` then `Wait-Process` (ends when the process is really gone).
- **Copy:** retried for up to 3 s, because the exe can stay locked briefly after exit.
- **Start:** polls every 100 ms; done once the log grew and stayed quiet for 300 ms, or after
  1 s without new log lines; at most 3 s.

Result (bus): `dev.ps1 -Fast` 5.6 s → 1.0 s; `dev.ps1` (release) ~19 s → ~14 s.
Use `-Fast` while editing and one plain `dev.ps1` at the end for the small exe.

## 3. Shared front end

- **`strip` module** (`src/strip.rs`): `Motion` holds glide, drag and zoom state and only
  answers with positions; the widget moves its own window (moving a window sends it messages,
  so doing it inside a borrow of the widget's state could re-enter). `move_strip` places a
  child or floating strip. 7 unit tests.
- **Moved onto it:** bus (`placement.rs`), weather (`label.rs`, taskbar client coordinates),
  media (`placement.rs`, done by the media session).
- **Popup host: not built.** The popup *rules* are already shared (`panel::PanelBehaviour`,
  `Fade`, `place`). What's left per widget is ~60 lines wiring them to windows that differ
  (bus hides its popup, weather destroys it, media has two panel modes). A trait-based host
  would cost more than the ~30 lines per widget it would save.

## 4. Drag bug: a wide strip couldn't take the far-right place

- **Symptom:** dragging media to the far right, the strip there never moved aside and the
  drop kept the old order.
- **Cause:** the old `insert_index` judged each neighbour separately: right-side neighbours by
  the dragged strip's right edge, left-side ones by its left edge. Media held against the
  tray is 294 px wide, so its right edge had passed bus's centre while its left edge hadn't
  passed weather's. Both counted, and the result was the old position.
- **Fix:** the dragged strip goes into the slot nearest to where it's held (all candidate
  slots computed with `place`, including obstacles). For normal widths this swaps at the same
  moment as before (halfway over the neighbour). 6 tests in `dock.rs`, including the measured
  case.
- **Checked on screen:** media dragged right takes the far right with bus moving aside; dragged
  back left, bus takes it back.

## 5. TaskbarWidgets (github.com/pfcdev/TaskbarWidgets)

MIT, C++/C#/Tauri, ~150 stars, last pushed 2026-08-05. Ideas taken, no code.

**How it differs from ours**

- Injects a DLL into Explorer and adds XAML elements to the taskbar's own visual tree (XAML
  Diagnostics). Their own risks document notes Windows updates can break it. Ours uses
  separate layered child windows: safer, no injection.
- Widgets are placed freely (anchor % + pixel offset), not stacked against the tray.
- Data comes from out-of-process providers writing atomic JSON snapshots; the Explorer side
  only renders and queues commands.

**Their drag handling** (`src/native/taskbar-hook/layout_math.h`, `taskbar_widgets_hook.cpp`)

- Free gaps are computed between obstacles; the widget goes into the gap under the cursor,
  else the one it was already in ("sticky"), else the nearest.
- While pinned against an obstacle edge, the grab offset is re-anchored to the cursor, so
  reversing the mouse reacts at once.
- Taskbar app buttons are read with UI Automation (cached 30 s) and projected as obstacles
  with 4 px clearance; other widgets get 4 px too.
- Drag threshold 4 px; a tap right after a drag is suppressed.
- Handles secondary-monitor taskbars (`Shell_SecondaryTrayWnd`).

**Adopted:** re-anchoring at the tray edge (`Motion::mouse_move` / `drag_x` take `max_x`).
Checked on screen: media dragged 600 px past the tray, then back 40 px, moves back 40 px
straight away (before: only after ~280 px).

**Candidates, not done**

| Idea | Value | Cost / open question |
|---|---|---|
| App icons as obstacles (UI Automation) | stops the stack covering icons with a centred taskbar and many apps | what to do on a collision: compact media, or hide a widget |
| Sticky slot (hysteresis) | no flicker at the halfway point | each widget computes the preview in its own process; drop and preview must agree |
| Second-monitor taskbars | widgets on other screens | strip per taskbar, separate order per taskbar |

**Not worth copying:** Explorer injection; free placement instead of the stack.

## 6. Later the same day: compact animation, right-edge fix, taskbar icons as obstacles

**Bug: a strip changing width moved away from the tray.** `UpdateLayeredWindow` without a
position keeps the left edge, so a strip switched to compact shrank away from its right
neighbour and then slid back (most visible with media). All three had it. Fix:
`strip::keep_right_edge` after every redraw that changed the width (when `Motion::settled`).

**Compact switch animates** (`Motion::resize`, `glide_ms`): media draws the full strip at the
in-between width (`layout::at_width`: text column narrows, then the gaps close; cover left,
buttons right); bus and weather draw the full content cut off with a 12 px fade. Any source of the
switch animates (right-click panel, settings file, the fit). Measured: right edges stayed put in
every sample (media 112 ↔ 258 px in ~125 ms).

**Icons as obstacles** (as in TaskbarWidgets: UIA `FindAll` of Button-type elements under the
taskbar, in its band, every 500 ms on a worker, an empty scan never replaces a good one):
- Only the leader (first member in dock order) scans; it publishes the buttons' right edge on its
  window (`TaskbarDock.IconsRight`), the others read it. Measured here: 363 (left-aligned, 7 apps).
- Members publish `FullWidth` (chosen mode), `MinWidth` (compact), `Stretch` (media). `dock::fit`
  decides from those, never from window sizes (no feedback loop): stretchable ones narrow first,
  then the others go compact (farthest from the tray first), then stretchable ones take back the
  leftover; if still short, the farthest one hides and the rest start again from full.
- A hidden member sets `TaskbarDock.Squeezed`: `dock::children` still lists it, so it keeps its
  place and the others keep counting it. Logged once when hidden / shown again (weather got a log:
  `%APPDATA%\TaskbarDock\taskbar-weather.log`).
- Drags stop at the buttons (`strip::Limits::min`), re-anchoring the grab point like at the tray.
- Weather on the left (`label_position`, or "auto" with a centred taskbar) leaves the stack
  (`dock::leave`); before, the others still counted it.
- Checked on screen with the test aid `TASKBAR_DOCK_TEST_ICONS_RIGHT=<x>` in the leader's (bus)
  environment: 1260 → media 231; 1400 → bus and weather compact, media 211; 1560 → media
  hidden; 1700 → all hidden; real → all back. Leader handover worked while bus restarted.

**Known limits:** a strip that appears (media starting to play) while there's no room shows for
up to 1 s before it hides (a strip not shown yet isn't in the taskbar's list, so it can't be
fitted). Bus's width changes with its text, so near the limit it may switch compact/full when
the times change. Neighbours follow a collapsing strip with a short glide, not in lockstep.
Not on screen yet: a real centred taskbar with many apps (only the user changes taskbar settings).

**Decided:** the user keeps a left-aligned taskbar and won't use a centred one. So no on-screen
test with a centred taskbar, and weather-on-the-left collisions are out of scope. With the
left-aligned taskbar a real collision needs ~19 more open apps; the fake-edge tests above cover it.

**Next (in order of value, all optional):**
1. A strip that appears with no room shows for up to 1 s first (see Known limits): fit it before
   showing (e.g. publish widths + set Squeezed before the first show, then let the fit decide).
2. Bus near the limit: maybe a small margin before switching back to full (all members must
   compute the same, so it can't depend on per-process timing).
3. Neighbours in lockstep while a strip collapses (now they glide after it).
4. Candidates from section 5 still open: sticky slot (hysteresis) while dragging; second-monitor
   taskbars (`Shell_SecondaryTrayWnd`).

## 7. New widget: Discord voice (`..\taskbar-discord`)

Inspired by TaskbarWidgets' `widgets/discord-voice`, but a different data source:

- **Theirs:** UI Automation on Discord's window (channel, names, mute/deafen from accessible
  names, with translated strings) + the `discord-webrtc_0` log (user ids, packet counters →
  speaking) + an optional admin service sniffing RTP with raw sockets for instant speaking.
  Measured here: that log gets stats every **10 s**, so without the service speaking is ~10 s late.
- **Ours (user's choice):** Discord's official local RPC pipe with the user's own Discord app
  (free; one-time client_id/secret + Authorize click). Instant SPEAKING_START/STOP, voice
  states, avatars from the CDN, and Mute/Deafen/Leave from the panel. Token DPAPI-encrypted.
- Taken from theirs: avatars as circles with a speaking ring, max 5 then "+N", hidden outside a call.
- Checked on screen with `TASKBAR_DISCORD_TEST=4`: docking (3 px gap, others reflow when it
  leaves), speaking ring, mute button round trip, leave → strip gone → rejoin, compact, setup
  panel. Real Discord: handshake framing verified (dummy client id → "Invalid Client ID").
  **With the user's app (same day):** sign-in, a real 7-person call, avatars and live speaking work.
  Not tried yet: Mute/Deafen/Leave on real Discord; token refresh (after ~7 days).

## 8. 2026-10-10: more from TaskbarWidgets (sticky slot, drop order, crash watchdog, settings lock)

Read their back end (`src/loader`: provider supervisor, atomic snapshots) and layout
(`layout_math.h`, `taskbar_widgets_hook.cpp`: greedy gap placement, sticky gap, drop override).
Not taken: free placement / percent anchors, a rotating slot for squeezed widgets (user: not needed).

- **Sticky slot** (`dock::sticky_index`, `track_drag`, `PROP_SLOT`): only the dragged widget
  decides its drop slot, with 10 px (at 100%) hysteresis past the halfway point, and publishes
  it on its window; the others' preview (`slot`) and `drop_reorder` use it, so they agree and
  the memory lives in one place. Measured with `_tmp\sticky_probe.ps1` (bus 199 px zoomed over
  weather, slots 1465/1546, halfway 1505): switches at x 1520 going right, back at x 1493.
- **Drop order** (their 3 s "drop override", our version): widgets call `drop_reorder` first and
  `set_dragging(false)` after, and `order.txt` is written atomically. Measured: after release
  weather goes 1465 → 1494 monotonically (follows bus shrinking from its zoom), no flick back.
- **Crash watchdog** (their `RunProviderIsolatedAsync`): the launcher stays after sign-in and
  restarts a widget it started that ended with an NTSTATUS error code (`panic = "abort"` gives
  0xC0000409), after 2, 4, 8, 16, 32 s; gives up after 5 crashes in 10 min. Exit 0 (Quit) and
  1 / -1 (Task Manager, `Stop-Process`, dev.ps1) are left alone. All four widgets call
  `crash::log_panics(log)` (before only media logged panics). Tested with a fake APPDATA and a
  `.cmd` exiting with 0xC0000409: exactly that log, then the launcher ended; exit 0 / -1: no restart.
  Note: a widget restarted by dev.ps1 isn't the launcher's child, so it isn't watched until the
  next sign-in.
- **Settings lock** (they have one writer; we have four): `settings::update` holds the named mutex
  `Local\TaskbarDock.Settings`; temp files are named per process; the rename retries for 200 ms.
  `tests/settings_lock.rs`: 8 threads × 25 updates = 200; without the lock it fails.
